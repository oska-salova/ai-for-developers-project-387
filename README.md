## Демо

Приложение: <https://ai-for-developers-project-386-vq2v.onrender.com/>

Сервис развёрнут на Render по free-тарифу: после простоя первый запрос может
открываться дольше обычного.

Render MCP не подключён: `mcp.render.com` недоступен из текущего региона,
поэтому деплой и управление сервисом выполняются через дашборд Render.

## Стек

- Frontend: Next.js 16, React, TypeScript
- Backend: Node.js, Express, TypeScript

## Установка

```bash
git clone https://github.com/oska-salova/ai-for-developers-project-387.git
cd ai-for-developers-project-387
```

Переменные окружения не обязательны: данные хранятся в памяти процесса, адрес API и CORS
имеют дефолты для локального запуска.

## Запуск

```bash
mise run setup
mise exec -- pnpm --dir backend dev          # с типом встречи «Знакомство»
mise exec -- pnpm --dir frontend dev
```

Фронтенд — http://localhost:3000, бэкенд — http://localhost:3001. В браузере запросы к API
идут на origin страницы: Next проксирует `/api` в бэкенд. Серверные компоненты обращаются к
`http://127.0.0.1:3001`; адрес переопределяется `API_URL`. `NEXT_PUBLIC_API_URL` (build-time)
задаёт внешний адрес API, если бэкенд живёт на другом origin, `CORS_ORIGIN` — разрешённый
origin фронтенда.

## Docker

Образ собирает обе части приложения и запускает их в одном контейнере. Наружу открыт только
порт из переменной `PORT` (по умолчанию `3000`):

```bash
docker build -t call-calendar .
docker run --rm -e PORT=8080 -p 8080:8080 call-calendar
```

Приложение будет доступно на http://localhost:8080. Next.js отдаёт интерфейс и проксирует
`/api` и `/health` во внутренний Express на порту 3001. `PORT` используется при деплое и в
автоматической проверке проекта; `NEXT_PUBLIC_API_URL` можно передать на сборке через
`--build-arg`, если API должен быть на отдельном публичном адресе.

Контракт API описан на TypeSpec в `contract/`: `mise run contract:build` генерирует OpenAPI,
SDK и типы бэкенда, `mise run contract:check` проверяет, что сгенерированное закоммичено.

## Проверки

```bash
mise run check    # быстрый гейт: контракт, SDK, формат, линтеры, типы, knip, тесты
mise run verify   # то же плюс Playwright; эту команду запускает CI
mise run security # уязвимости зависимостей, история git, онлайн-проверка workflow
```

В CI (`.github/workflows/ci.yml`) две джобы: `Verify` — `mise run verify` и `Security` —
`mise run security`. Релизы ведёт `release-please.yml`, проверку Хекслета — `hexlet-check.yml`.

## Агент в комментариях

`.github/workflows/opencode.yml` запускает OpenCode в GitHub Actions: напишите `/oc` или
`/opencode` в комментарии к issue, PR или к строке во вкладке «Files» — агент прочитает задачу,
внесёт правки и либо ответит в треде, либо откроет PR. Команда должна стоять в начале
комментария или после пробела в той же строке.

- Модель — `opencode/deepseek-v4.1-flash`, сессия не публикуется на opencode.ai.
- Запускать может только владелец репозитория: комментарии остальных job не запускают.
- Перед первым использованием нужно установить приложение
  [opencode-agent](https://github.com/apps/opencode-agent) и добавить секрет `OPENCODE_API_KEY`.
- Обычный `/oc` не получает `GH_TOKEN`: `GITHUB_TOKEN` в нём только на чтение, а комментарии
  и пуш выполняются токеном приложения через OIDC. Тайм-аут — 30 минут, одновременно в одном
  issue или PR идёт один запуск.
- Если в комментарии назван скилл `triage`, `to-spec` или `to-tickets` (например,
  `/oc запусти скил to-spec` или `/oc to-spec`), запускается отдельный job с `issues: write`
  и `GH_TOKEN`: агент может читать и создавать issue, но не может пушить код. Остальные
  `/oc`-задачи работают без `GH_TOKEN`.
- `to-spec` и `to-tickets` интерактивные: первый запуск показывает швы или список тикетов,
  второй — публикует. Второй комментарий тоже должен называть скилл, иначе запуск уйдёт в job
  без права записи.
- В CI агенту доступны `AGENTS.md`, `docs/agents/` и скиллы из `.agents/skills/`; имя скилла
  в комментарии — команда загрузить его по ID. `wayfinder` и скиллы, которым нужна запись
  в файлы, по-прежнему запускаются локально.

### Автотриаж новых обращений

`.github/workflows/opencode-triage.yml` запускается на `issues: opened` и публикует один
комментарий с разбором, сценариями и рекомендованными метками. Код он не меняет.

- Запуск только для `OWNER`, `MEMBER` и `COLLABORATOR`: репозиторий публичный.
- Issue с меткой `ready-for-agent` пропускаются: так `to-spec` и `to-tickets` защищают
  опубликованные спецификации и тикеты от повторного разбора.
- Тайм-аут — 10 минут; одновременно идёт один запуск на issue.
- Проверка: новое issue от владельца получает комментарий, issue с `ready-for-agent` даёт
  запуск `skipped` без комментария.

## Использование

В приложении два типа пользователей: владелец календаря (задаёт типы встреч и смотрит записи)
и гость (выбирает свободное время и записывается на звонок). Регистрации и авторизации нет.

Правила записи:

- Окно записи — 14 календарных дней, начиная с сегодняшнего дня; окно сдвигается с течением времени.
- Рабочие часы владельца: 09:00–18:00, часовой пояс Europe/Moscow.
- Шаг доступных стартов — 15 минут; длительность слота равна длительности типа встречи.
- Пересечение интервалов запрещено, включая частичное наложение разных типов встреч.
- Следующая встреча может начинаться в момент окончания предыдущей.
- Правила действуют и для запросов, пришедших одновременно: время занимает тот, кто записался первым.

## Сценарий владельца

1. Владелец открывает раздел «Типы встреч» и создаёт тип встречи: название, описание, длительность.
2. Владелец открывает раздел «Встречи» и видит список предстоящих встреч.

## Сценарий гостя

1. Гость нажимает «Записаться» — открывается список типов встреч, и он выбирает нужный.
2. Гость видит календарь на ближайшие 14 дней: свободные слоты доступны для выбора,
   занятые отображаются, но недоступны.
3. Гость выбирает свободный старт, указывает имя и почту и подтверждает запись.
4. Выбранное время становится занятым и больше не предлагается никому.

## Ограничения

- Регистрации и авторизации нет: разделы открыты всем.
- Владелец календаря в приложении один и задан заранее.
- Данные хранятся в памяти процесса: перезапуск сервера сбрасывает созданные типы встреч и
  записи, календарь возвращается к одному стартовому типу «Знакомство».
