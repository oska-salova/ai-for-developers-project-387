# Критерии ревью pull request

Документ — источник истины для независимого авторевью и для человека-ревьюера.
Каждый критерий имеет ID, способ проверки и допустимое свидетельство. Вердикт без
свидетельства по критерию считается невыполнением критерия, а не «мелким замечанием».

Источники истины проекта: [`AGENTS.md`](./AGENTS.md), [`GLOSSARY.md`](./GLOSSARY.md) и
[`docs/adr/`](./docs/adr/).

## Severity

- **blocker** — нарушает контракт, теряет данные, ломает основной сценарий, открывает запись
  без права на неё или делает проверку недостоверной. Мержить нельзя.
- **major** — нарушает заявленное поведение или документированное правило, но не разрушает
  основной сценарий; исправляется в этом PR либо получает отдельный тикет со ссылкой.
- **minor** — локальная неточность, читаемость, формулировка или отсутствие пояснения; не
  меняет поведение.

## Критерии

### CONTRACT-1 — TypeSpec первичен

Единственный источник истины API — `contract/main.tsp` ([ADR-0001](./docs/adr/0001-typespec-source-of-truth.md)).
Сгенерированные `contract/openapi/**`, `frontend/src/lib/api/generated/**` (включая `dist/`) и
`backend/src/generated/**` не правятся руками: изменение начинается с `.tsp`, затем
`mise run contract:build`, и только потом меняется код.

**Проверка.** В диффе нет ручных правок сгенерированных путей; каждое изменение контракта
сопровождается правкой `contract/main.tsp`; `mise run contract:build` не оставляет
незакоммиченного диффа; `mise run contract:check` зелёный.

**Допустимое свидетельство.** Ссылка на прогон `contract:check`/`mise run verify` с head SHA,
плюс diff, где видно `.tsp` и перегенерированные артефакты одним изменением. Скриншот или
цитата вывода `contract:check` без ссылки на прогон не считается.

### CONTRACT-2 — Express-роуты руками по сгенерированным типам

Роуты Express 5 написаны вручную по типам из `backend/src/generated/openapi.d.ts`
([ADR-0002](./docs/adr/0002-hand-written-express-routes.md)); серверный генератор TypeSpec не
подключён. Соответствие реальных ответов контракту проверяет
`backend/src/app.contract.test.ts` (коды и тела по `contract/openapi/openapi.json`).

**Проверка.** Новый или изменённый роут есть и в `contract/main.tsp`, и в `backend/src/app.ts`;
типы взяты из `components["schemas"]`; contract compliance тест покрывает успешный и ошибочные
ответы изменённого маршрута.

**Допустимое свидетельство.** Ссылка на прогон
`mise exec -- pnpm --dir backend test src/app.contract.test.ts` с head SHA и имена тестов,
проверяющих код и тело ответа. Утверждение «тест есть» без ссылки на прогон не принимается.

### API-1 — Рамка ошибок, коды и дословные тексты

Все ошибки отдаются как `{ error: { code, message, fields? } }` с кодами
`validation_error`, `not_found`, `slot_conflict`, `internal_error`
([ADR-0006](./docs/adr/0006-error-frame-and-check-order.md)). Порядок проверок: тело →
существование типа → правила слота → пересечение. Тексты русские и являются частью контракта:
UI показывает их дословно. Ответ `204` не имеет тела и заголовка `content-type`.

**Проверка.** Коды и тексты совпадают с контрактом и тестами дословно; `fields` собираются за
один проход в порядке полей контракта; невалидное тело важнее неизвестного типа (`400`, не
`404`), неверный `start` важнее занятого слота (`400`, не `409`); для `204` в коде стоит
`res.status(204).end()` (или эквивалент) и тест проверяет отсутствие тела и `content-type`.

**Допустимое свидетельство.** Ссылка на прогон API-тестов и contract compliance теста с head
SHA; цитата из теста, проверяющего точную строку сообщения и отсутствие тела у `204`.

### DATA-1 — Хранилище в памяти и синхронная вставка

Типы встреч и встречи живут в замыкании `createStore()`, базы нет
([ADR-0004](./docs/adr/0004-in-memory-store.md)). `addMeeting` синхронно проверяет пересечение
и вставляет встречу; между проверкой и вставкой нет `await`, поэтому гонку выигрывает первый
([ADR-0005](./docs/adr/0005-first-wins-synchronous-insert.md)). Идемпотентности у
`POST /api/meetings` нет.

**Проверка.** В `backend/src/store.ts` нет асинхронных методов и `await` внутри `addMeeting`;
новые зависимости не тянут БД и внешнее хранилище; есть тест, что результат `addMeeting` не
является thenable (`expect(result).not.toHaveProperty("then")` или
`expect(result).not.toBeInstanceOf(Promise)`); тест гонки десяти параллельных POST даёт один
`201` и девять `409`.

**Допустимое свидетельство.** Ссылка на прогон `backend`-тестов с head SHA и имена тестов на
thenable и гонку. Комментарий в коде без исполняемого теста доказательством не считается.

### DATA-2 — Согласованность после мутации

После создания типа, записи гостя или любой другой мутации список встреч, занятость и сетка
слотов согласованы: занятая встреча исчезает из доступных слотов, список `GET /api/meetings`
содержит её с типом встречи, длительность берётся из типа, а не из снимка.

**Проверка.** Тест выполняет мутацию, затем читает `GET /api/meetings` и
`GET /api/meeting-types/:id/slots` и сверяет, что занятый интервал помечен `available: false`
(включая частичное наложение разных типов), а список встреч отсортирован по старту и содержит
актуальную сводку типа.

**Допустимое свидетельство.** Ссылка на прогон соответствующего интеграционного теста с head
SHA и имена тестов, где мутация и последующее чтение находятся в одном сценарии.

### SLOT-1 — Правила окна и сетки

Окно записи — 14 календарных дней, начиная с сегодняшнего дня владельца. Рабочие часы —
09:00–18:00 Europe/Moscow с фиксированным смещением `+03:00`; шаг старта — 15 минут.
Пересечения интервалов запрещены, стык разрешён (встреча может начаться ровно в момент
окончания предыдущей). При одновременных запросах слот занимает первый дошедший до вставки
([ADR-0007](./docs/adr/0007-time-and-booking-window.md)).

**Проверка.** Все правила живут в `backend/src/owner-time.ts` и `backend/src/time-rules.ts` и
используются движком слотов, валидацией `start` и хранилищем; `now` инъектируется; тесты
фиксируют `now` и проверяют границу суток MSK, 14 дней, 09:00/17:45, шаг 15 минут, частичное
наложение, разрешённый стык и гонку; серверный часовой пояс не влияет на результат.

**Допустимое свидетельство.** Ссылка на прогон `owner-time`, `slots`, `app.slots` и
`app.meetings` тестов с head SHA и имена тестов на границы и стык. Один счастливый путь без
границ недостаточен.

### UI-1 — HTTP только через SDK

Фронтенд ходит в API только через сгенерированный SDK; прямые `fetch`, `XMLHttpRequest`,
`axios` и другие HTTP-клиенты запрещены ([ADR-0003](./docs/adr/0003-sdk-only-http.md)).
Базовый URL и маппинг ошибок в `ApiError` живут только в `frontend/src/lib/api.ts`; текст
ошибки сервера показывается дословно.

**Проверка.** `mise run sdk:check` зелёный; новые запросы идут через функции `lib/api.ts`;
`ApiError` содержит `code`, `message` и `fields`; компоненты не придумывают своих формулировок
для `400`, `404` и `409` и не теряют серверный текст.

**Допустимое свидетельство.** Ссылка на прогон `sdk:check`/`mise run verify` с head SHA и
тест компонента или модуля, где показан дословный текст серверной ошибки. Скриншот без
ссылки на прогон не принимается.

### UI-2 — Вендорные компоненты и безопасный рендер

`frontend/src/components/ui/*` — вендорный shadcn/ui, добавленный через
`mise exec -- pnpm dlx shadcn@latest add <component>`; пакета `shadcn` в зависимостях нет.
Тёмная тема — класс `.dark` на `<html>`, а не `prefers-color-scheme`. В серверных компонентах
нет `new Date()`, `Math.random()` и `crypto.randomUUID()`: с `cacheComponents` они ломают
пререндер.

**Проверка.** В диффе `ui/*` меняется только осознанно и локально; `package.json` и lockfile
не содержат `shadcn`; тема переключается классом `.dark`; в серверных компонентах нет
недетерминированных вызовов, время приходит через `env` или `<Suspense>` с
`await connection()`; `next build` зелёный.

**Допустимое свидетельство.** Ссылка на прогон `mise run verify` (в нём есть `next build`) с
head SHA и diff зависимостей/компонентов. Утверждение «локально собирается» без прогона не
считается.

### TEST-1 — Швы тестирования

Бэкенд тестируется HTTP-контрактом через supertest и `createApp({ store, now })` со свежим
хранилищем и фиксированными часами. Фронтенд — компонентные тесты с моками SDK и
`next/navigation`; маршрутные тесты, проверяющие несколько страниц, лежат в `src/app/`; e2e —
в `frontend/e2e` (`*.spec.ts`), только Chromium, против production-сборки и бэкенда `dev` на 3001.

**Проверка.** Новое поведение проверяется на своём шве: бэкенд не мокает `store`, а получает
его зависимостью; фронтенд не ходит в сеть из компонентного теста; e2e не подменяет SDK и
работает с реальным сервером; часы и случайность инъектируются.

**Допустимое свидетельство.** Ссылка на прогон соответствующего набора с head SHA и имена
тестов, показывающие используемый шов (например, `createApp({ store, now })` в бэкенд-тесте).

### TEST-2 — Тест проверяет поведение, а не реализацию

Тест описывает наблюдаемый контракт: HTTP-код, тело, текст ошибки, доступность слота,
отображение в интерфейсе. Он не завязан на приватные функции, порядок вызовов, структуру
компонента или реализацию хранилища.

**Проверка.** При рефакторинге без изменения поведения тест остаётся зелёным; в тесте нет
проверок внутренних вызовов и снапшотов всей разметки ради самой разметки; утверждения
читаются как сценарий пользователя.

**Допустимое свидетельство.** Ссылка на прогон с head SHA и сам тест: утверждения на
публичном результате. Тест, который проходит только при конкретной реализации, — нарушение.

### CASE-1 — Основной, негативный и соседний сценарии

Покрыты основной сценарий спеки, негативный (невалидные данные, занятый слот, неизвестный
тип, недоступный сервер) и соседний (граница окна, стык интервалов, повторный клик,
одновременная запись). Показан красный прогон: тест действительно падал до исправления.

**Проверка.** В PR есть ссылки на зелёный прогон и на красный прогон (или лог падения) для
нового теста; сценарии названы явно и соответствуют спеку/тикету, а не только коду.

**Допустимое свидетельство.** Ссылки на оба прогона с head SHA плюс имена тестов. Красный
прогон, описанный словами без ссылки или лога, не принимается.

### PR-1 — Тело PR по шаблону

Тело PR заполнено по [`.github/pull_request_template.md`](./.github/pull_request_template.md):
есть ссылки на обращение, спеку и тикеты; в «Проверках» у каждой строки есть команда, ссылка
на прогон и SHA, совпадающий с head PR; «Риск» называет ломаемое поведение и затронутых;
«Откат» даёт команду Git и способ проверить восстановление поведения.

**Проверка.** Заголовок PR — Conventional Commits со ссылкой на тикет; заявленный SHA равен
`headRefOid` PR; ссылки на прогоны открываются и относятся к этому коммиту; риск и откат
конкретны.

**Допустимое свидетельство.** Сам PR и `gh pr view <номер> --json body,headRefOid`; сверка
каждого заявленного прогона через
`gh api repos/<owner>/<repo>/actions/runs/<id> --jq '{conclusion, head_sha}'`.

### STD-1 — Стандарты репозитория

Коммиты — Conventional Commits со ссылкой на тикет (`feat: запись на свободный слот (#12)`).
Зависимости фиксируются точными версиями, без `^`. Отключённых правил линтеров нет; исключения
допустимы только узкие (путь + правило) с причиной и датой пересмотра.

**Проверка.** Заголовки коммитов и PR проходят commitlint; в `package.json`/lockfile нет
диапазонов версий; в конфигах нет новых отключений без обоснования; `mise run check` зелёный.

**Допустимое свидетельство.** Ссылка на прогон `mise run check`/`mise run verify` с head SHA,
`git log --oneline` и diff зависимостей/конфигов линтеров.

### DOC-1 — Документация обновлена

Если менялось поведение, обновлены `README.md`, `AGENTS.md`, `GLOSSARY.md` и/или `docs/adr/`:
новые правила, термины, ограничения и причины решений не остаются только в коде.

**Проверка.** Diff кода и diff документации согласованы; новый термин есть в `GLOSSARY.md`;
изменение архитектурного решения оформлено ADR; команды и переменные окружения описаны там,
где их будут искать.

**Допустимое свидетельство.** Список изменённых документов в PR с ссылками на строки; для
отсутствия изменений — объяснение, почему поведение не менялось.

### SCOPE-1 — Границы проекта

Нет авторизации и регистрации, писем, базы данных и второго инстанса: приложение рассчитано
на одного владельца, одного процесса и память процесса.

**Проверка.** Diff не добавляет аутентификацию, отправку почты, ORM/БД, очередь, второй сервис
или горизонтальное масштабирование; зависимости и конфиги не тянут эти возможности косвенно.

**Допустимое свидетельство.** Diff зависимостей и конфигов плюс явная проверка новых файлов и
маршрутов. Расширение границ требует отдельного решения и ADR, а не «попутной» правки.

## Формат вердикта

Заголовок вердикта обязателен и содержит три отпечатка:

```text
REVIEW.md@<12 hex-символов sha256>
шаблон@<12 hex-символов sha256>
head@<40 hex-символов head SHA PR>
```

`head@` обязателен: без него вердикт недействителен. Отпечатки `REVIEW.md` и шаблона берутся
из текущей ветки PR; head — фактический `headRefOid` проверяемого PR.

Дальше идут блоки в этом порядке:

```markdown
## Тело PR

Соответствие шаблону, ссылки на обращение/спеку/тикеты, сверка заявленных прогонов и SHA.

## Спецификация

| ID         | Статус       | Свидетельство        |
| ---------- | ------------ | -------------------- |
| CONTRACT-1 | выполнено    | <ссылка/файл:строка> |
| ...        | не выполнено | нет                  |

## Стандарты

Коммиты, зависимости, линтеры, документация.

## Риск и откат

Что может сломаться, кого затрагивает, достаточна ли глубина проверки; команда Git для
отката и способ проверить восстановление.

## Замечания

**З-1** blocker CONTRACT-1 contract/main.tsp:12 — что не так; как исправить.
**З-2** major API-1 backend/src/app.ts:140 — что не так; как исправить.
Замечание без ID помечается «вне критериев».

## Что проверено

Список прочитанных файлов, запущенных проверок и сверенных прогонов.
```

Правила:

- Каждое замечание нумеруется `**З-N**` и содержит severity, ID критерия, `файл:строка`,
  описание проблемы и конкретное исправление.
- Замечание без ID критерия помечается «вне критериев» и не влияет на статус критериев.
- Критерий без свидетельства считается **невыполненным**, даже если замечаний по нему нет.
- Статусы в таблице: `выполнено`, `не выполнено`, `не применимо` (с обоснованием).
