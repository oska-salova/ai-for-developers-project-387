# Критерии ревью календаря звонков

Документ для двух читателей: независимого ревьюера в
`.github/workflows/opencode-review.yml` и человека, который решает о мерже.
Здесь — общие инварианты сервиса. Требования к конкретной доработке живут в
спецификации и тикетах: `REVIEW.md` их не заменяет, а проверяет, что работа не
нарушила ничего вокруг.

- Область: `backend/`, `frontend/`, `contract/`, `docs/`, `.github/`.
- Версия зафиксирована в заголовке вердикта (`REVIEW.md@<хеш>`); ревьюер читает
  файл из текущей ветки PR.
- Изменение этого файла в PR — предмет ревью. Ослабление существующей проверки
  без обоснования в теле PR — `blocker`; решение принимает человек при мерже.
- Пересмотр: 13.11.2026.

## Как пользоваться

Каждый критерий имеет ID. По каждому ID ревьюер отвечает одним из трёх:
`выполнено`, `не выполнено`, `не применимо` — с причиной. Ссылка на ID
обязательна в каждом замечании. Замечание без подходящего ID помечается
`вне критериев`, и в нём предлагается формулировка нового критерия.

**Свидетельство** — то, что можно открыть: путь и строка, имя теста, ссылка на
прогон с SHA. «Код выглядит правильно» свидетельством не является: критерий без
свидетельства считается невыполненным.

## Контракт и API

### CONTRACT-1 — Контракт первичен

Изменение API начинается в `contract/main.tsp`. Сгенерированные
`contract/openapi/**`, `frontend/src/lib/api/generated/**`,
`backend/src/generated/**` получены генерацией и не правятся руками
(ADR-0001).

- Проверка: `mise run contract:check`, диф `contract/main.tsp` и сгенерированных.
- Свидетельство: зелёный `contract:check` при неизменных сгенерированных файлах.

### CONTRACT-2 — Роуты пишутся руками по контракту

Express-роуты соответствуют типам из `backend/src/generated/openapi.d.ts`, а
расхождение ответов ловит contract compliance тест (ADR-0002).

- Проверка: диф `backend/src/app.ts` и `backend/src/app.contract.test.ts`.
- Свидетельство: contract-тест покрывает новые коды и тела ответов.

### API-1 — Рамка ошибок и тексты — часть контракта

Ошибки отдаются как `{ error: { code, message, fields? } }` с кодами
`validation_error`, `not_found`, `slot_conflict`, `internal_error`; новых
машинных кодов не вводим, порядок проверок фиксирован, `message` на русском и
показывается интерфейсом дословно (ADR-0006). Успешный ответ без тела не несёт
`content-type`.

- Проверка: диф роутов и сообщений, тесты на код и текст ответа.
- Свидетельство: тест, который утверждает `code` и `message` дословно.

## Данные и слоты

### DATA-1 — Синхронное хранилище в памяти

Данные живут в `createStore()`, база не появляется (ADR-0004). Мутирующие
операции синхронные: между проверкой и вставкой нет `await`, иначе теряется
гарантия «первый победил» (ADR-0005).

- Проверка: диф `store.ts`; отсутствие `async`/`await` в операциях мутации.
- Свидетельство: тест на то, что результат операции не является thenable.

### DATA-2 — Согласованность после мутации

После любой мутации список встреч, занятость и сетка доступных слотов
согласованы: удалённая встреча не занимает время, добавленная занимает,
соседние записи не меняются.

- Проверка: тест «следующий запрос слотов после мутации».
- Свидетельство: HTTP-тест на освободившийся или занятый слот.

### SLOT-1 — Правила записи

Окно 14 календарных дней, рабочие часы 09:00–18:00 Europe/Moscow с
фиксированным смещением +03:00 (ADR-0007), шаг стартов 15 минут, пересечения
запрещены включая частичные, стык разрешён, из одновременных запросов выигрывает
первый.

- Проверка: тесты слотов и HTTP-тесты с фиксированными часами.
- Свидетельство: тесты на границы окна, частичное наложение и стык.

## Интерфейс

### UI-1 — HTTP только через SDK

Запросы идут через сгенерированный SDK; базовый URL и маппинг ошибок в
`ApiError` — только в `frontend/src/lib/api.ts` (ADR-0003).

- Проверка: `mise run sdk:check`; диф без прямых `fetch` и сторонних клиентов.
- Свидетельство: зелёный `sdk:check` и компонентный тест на текст `ApiError`.

### UI-2 — Вендорные компоненты и ограничения Next.js

`frontend/src/components/ui/*` добавляются через shadcn CLI; пакет `shadcn` в
зависимости не попадает. Тема переключается классом `.dark`. В серверных
компонентах нет `new Date()`, `Math.random()` и `crypto.randomUUID()` — они
ломают пререндер при включённых `cacheComponents`.

- Проверка: диф зависимостей и компонентов, зелёный `mise run verify`.
- Свидетельство: `frontend/package.json` без `shadcn` и прогон сборки.

## Тесты

### TEST-1 — Тесты на согласованных швах

Бэкенд — supertest через `createApp({ store, now })` с фиксированными часами и
свежим хранилищем. Фронтенд — компонентные тесты рядом с кодом с моками SDK и
`next/navigation`, маршрутные — в `src/app/`. E2E — `frontend/e2e` против
production-сборки и реального бэкенда на 3001.

- Проверка: расположение и шов новых тестов.
- Свидетельство: тесты именно на этих швах, без обхода публичного поведения.

### TEST-2 — Тест проверяет поведение, а не реализацию

Утверждения — про коды и тела HTTP, видимые элементы, отправленные вызовы SDK и
итоговое состояние. Внутренние функции, приватные структуры и снимки реализации
не тестируются.

- Проверка: чтение диффа тестов.
- Свидетельство: тест падал бы при изменении поведения, а не при рефакторинге.

### CASE-1 — Сценарии спецификации покрыты

Основной, негативный и соседний сценарии из спецификации имеют тесты; отказ при
нарушенном поведении показан, а не описан словами.

- Проверка: сверка списка сценариев с набором тестов, ссылки в теле PR.
- Свидетельство: ссылка на упавший прогон до исправления и зелёный после.

## Процесс

### CI-1 — Публикация переживает повторный запуск

Публикующая джоба обязана переживать повторный запуск после сбоя: результат
завершённого прогона остаётся доступным — ветка и/или открытый PR, — а
перезапуск не падает на уже существующей ветке и не правит закрытый PR.

- Проверка: чтение шага публикации; сценарии «ветка с тем же именем уже есть» и
  «PR по этой ветке закрыт».
- Свидетельство: пуш в свежую ветку при конфликте имени, обновление только
  открытого PR, внятная ошибка вместо молчаливой правки чужого треда.

### STD-1 — Коммиты, гейты и зависимости

Conventional Commits со ссылкой на тикет в коммите реализации; `mise run check`
зелёный; после изменения зависимостей — `mise run security`. Версии фиксируются
точно, без `^`. Сгенерированное и `.github/workflows/hexlet-check.yml` руками не
правятся. Отключённых правил линтеров без узкого исключения с причиной нет.

- Проверка: `git log`, прогоны, диф `package.json` и конфигов линтеров.
- Свидетельство: зелёные прогоны и заголовки коммитов.

### DOC-1 — Документация следует за поведением

Изменение, затрагивающее `README.md`, `AGENTS.md`, `GLOSSARY.md` или
`docs/adr/`, отражено в них. Новый термин идёт в глоссарий, архитектурное
решение — в ADR.

- Проверка: диф документов рядом с диффом кода.
- Свидетельство: обновлённые разделы.

### SCOPE-1 — Рамки учебного проекта

Авторизации, писем гостю, базы данных, второго инстанса и новых типов сущностей
не появляется (ADR-0004). Расширение рамок оформляется отдельным решением, а не
попутно в тикете.

- Проверка: диф зависимостей, структуры и тела PR.
- Свидетельство: явное «нет» в теле PR и отсутствие новых зависимостей.

## Severity

- `blocker` — ломает поведение, контракт или инвариант; мерж невозможен.
- `major` — нарушает критерий, последствие ограничено; исправить или обосновать.
- `minor` — стиль, читаемость, мелкая неточность; на усмотрение человека.

Отсутствие рефакторинга вне области и вкусовые предпочтения — не более чем
`minor`: тикет не расширяем.

## Формат вердикта

Один комментарий в PR, markdown, по-русски. Заголовок одной строкой:

```
REVIEW.md@<REVIEW_SHA> · шаблон@<TEMPLATE_SHA> · head@<HEAD_SHA>
```

`head@<HEAD_SHA>` обязателен: без него вердикт недействителен. Далее разделы в
этом порядке:

1. `## Вердикт` — одна строка: можно ли мержить и что мешает.
2. `## Тело PR` — по разделу шаблона: замечание или «ок».
3. `## Спецификация` — таблица: ID критерия | статус | свидетельство.
4. `## Стандарты` — по ID из разделов выше.
5. `## Риск и откат` — достаточность проверок последствиям ошибки.
6. `## Замечания` — `**З-N** <severity> <ID> <файл>:<строка> — что не так, как
   исправить`. Не больше 10; остальное одной строкой «прочее: N однотипных мест».
7. `## Что проверено` — явный список, чтобы «замечаний нет» отличалось от
   «не смотрел».

Без похвалы и без пересказа диффа.
